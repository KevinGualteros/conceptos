CLOUD COMPUTING

Computación en la nube

La nube permite consumir capacidad de cómputo, almacenamiento, redes y plataformas mediante servicios gestionados. Para elegir una solución compara requisitos, modelo operativo, seguridad, resiliencia y costo.

Conceptos base Arquitectura Entrevistas

Conceptos, herramientas y ejemplos

IaaS, PaaS y SaaS

IaaS entrega recursos de infraestructura como máquinas virtuales, redes y discos; el cliente administra sistema operativo y aplicaciones. PaaS abstrae parte del sistema operativo y runtime para centrarse en el código. SaaS entrega una aplicación lista para usar.

No son niveles absolutos: las responsabilidades cambian según el servicio concreto.

Región, zona y edge

Una región es un área geográfica del proveedor; las zonas de disponibilidad aíslan fallos dentro de una región. Los puntos edge acercan ciertos servicios a los usuarios. Alta disponibilidad entre zonas no equivale automáticamente a recuperación ante desastre entre regiones.

Escalabilidad y elasticidad

Escalabilidad vertical : aumentar recursos de una instancia. Horizontal : añadir instancias o réplicas. Elasticidad : ajustar capacidad según la demanda. El escalado requiere métricas, límites y pruebas para evitar amplificar un incidente.

Alta disponibilidad y recuperación

Define RTO (tiempo objetivo para recuperar) y RPO (pérdida de datos tolerable medida en tiempo). Diseña redundancia, backups, pruebas de restauración y runbooks según el impacto del fallo.

Responsabilidad compartida

El proveedor protege y opera componentes de la nube; el cliente configura identidades, permisos, datos, red y sistemas según el servicio. En una VM hay más responsabilidad del cliente que en una función administrada o una aplicación SaaS.

Preguntas frecuentes y de entrevista

¿La nube siempre es más económica?

No necesariamente. Conviene comparar costo total, utilización, costos de egreso, operación, licencias, resiliencia y compromisos de uso. El dimensionamiento y la limpieza de recursos son fundamentales.

¿Qué diferencia hay entre alta disponibilidad y recuperación ante desastre?

La alta disponibilidad reduce interrupciones durante fallos esperados o localizados. La recuperación ante desastre restaura el servicio tras un evento mayor y suele incluir objetivos RTO/RPO, respaldos y una estrategia geográfica.

¿Cuándo usar un servicio administrado?

Cuando reduce carga operativa sin sacrificar controles o capacidades necesarias. Aun así, hay que configurar seguridad, observabilidad, límites, backups cuando corresponda y costos.

¿Qué es el vendor lock-in?

Dependencia de APIs, datos o servicios específicos de un proveedor. Puede ser aceptable si el valor compensa el costo de migración; abstraer todo por anticipado también añade complejidad.

CLOUD PROVIDER

Amazon Web Services (AWS)

AWS ofrece servicios de infraestructura, datos, redes, seguridad y aplicaciones. Diseña con permisos mínimos, redes bien segmentadas, telemetría y controles de costo; valida siempre el comportamiento en la documentación del servicio y la región.

Compute Networking IAM Observabilidad

Conceptos, herramientas y ejemplos

Modelo global: regiones y zonas

Las regiones contienen varias zonas de disponibilidad independientes. Colocar componentes críticos en zonas distintas ayuda frente a fallos zonales; la réplica entre regiones se diseña aparte y depende de los servicios utilizados.

Acceso a AWS: consola, CLI y SDK

La consola sirve para exploración; AWS CLI facilita scripts reproducibles; los SDK integran servicios desde el código. Para tareas de automatización prefiere roles y credenciales temporales a claves estáticas almacenadas en repositorios. 

aws sts get-caller-identity
aws configure list
aws ec2 describe-instances --region us-east-1
Diseño seguro de una cuenta

Usa IAM Identity Center o roles federados cuando corresponda, MFA para acceso humano, separación de ambientes/cuentas, CloudTrail, budgets, etiquetas y políticas organizacionales. Evita claves de acceso root para el trabajo cotidiano.

Red de referencia

VPC, subredes, tablas de rutas, Security Groups, Network ACL, Internet Gateway y NAT Gateway cumplen funciones distintas. Que una subred se llame “pública” no basta: revisa rutas, direcciones y reglas.

Despliegue y operación

Versiona infraestructura con Terraform o CloudFormation, empaqueta apps en contenedores cuando tenga sentido, automatiza validaciones y define métricas/alertas. Un despliegue debe ser repetible, auditable y reversible.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

aws sts get-caller-identity
aws s3 ls
aws ec2 describe-vpcs --region us-east-1

Errores frecuentes y diagnóstico

AccessDenied

Comprueba identidad efectiva, política IAM, permisos de recurso, SCP, permissions boundary y condiciones; identifica la acción y el ARN exactos del error.

Timeout o recurso inaccesible

Comprueba DNS, rutas, Security Groups, Network ACL, endpoints, puertos, health checks y logs antes de cambiar reglas de seguridad de forma amplia.

Preguntas frecuentes y de entrevista

¿EC2 o Lambda?

EC2 ofrece control del servidor y del sistema operativo. Lambda ejecuta funciones bajo demanda y reduce la gestión del servidor, con límites y modelo de ejecución propios.

¿S3, EBS o EFS?

S3 es almacenamiento de objetos; EBS ofrece bloques para instancias compatibles; EFS es un sistema de archivos administrado compartible entre clientes compatibles.

¿Security Group o Network ACL?

Security Groups son stateful y se asocian a interfaces/recursos compatibles. Network ACL son stateless y filtran tráfico a nivel de subred; hay que considerar reglas en ambos sentidos.

¿Qué diferencia hay entre CloudWatch y CloudTrail?

CloudWatch se centra en métricas, logs, alarmas y observabilidad. CloudTrail registra actividad de API y ayuda a auditar acciones en la cuenta.

¿Cómo reduzco costos sin afectar producción?

Mide primero; revisa utilización, recursos huérfanos, almacenamiento, transferencia y opciones de compra. Prueba cambios, define límites y evita eliminar recursos sin revisar dependencias.

¿Para qué sirve IAM Role?

Permite asumir permisos temporalmente mediante credenciales temporales, útil para usuarios federados, servicios y workloads sin repartir claves permanentes.

Preguntas frecuentes y de entrevista

¿Cómo elegir entre dos servicios que se solapan?

Empieza por requisitos de carga, modelo de datos, latencia, disponibilidad, compatibilidad, carga operativa, controles y costo total; después valida límites y comportamiento en documentación.

¿Puedo ejecutar los comandos directamente en cualquier cuenta?

No. Necesitas AWS CLI, identidad válida, región correcta y permisos. Los nombres de bucket, IDs y parámetros son ejemplos, no recursos existentes.

¿Qué patrón de seguridad debo aplicar?

Mínimo privilegio, redes segmentadas, datos cifrados, secretos fuera del código, logs protegidos y restauraciones probadas. Ajusta los controles al riesgo real.

Preguntas frecuentes y de entrevista

¿Qué es AWS?

Plataforma de servicios cloud para ejecutar aplicaciones, almacenar datos, construir redes y usar servicios gestionados.

¿EC2 o Lambda?

EC2 da control sobre instancias y sistema operativo; Lambda ejecuta funciones bajo demanda sin administrar directamente los servidores. Elige por duración, runtime, control y eventos.

¿S3, EBS y EFS?

S3 guarda objetos, EBS aporta almacenamiento de bloques para instancias compatibles y EFS ofrece un sistema de archivos compartido administrado.

¿RDS o DynamoDB?

RDS administra motores relacionales con SQL y relaciones; DynamoDB es NoSQL de clave-valor/documentos y se diseña alrededor de los patrones de acceso.

¿Security Group y NACL?

Security Group es stateful y se aplica a interfaces/recursos compatibles; NACL es stateless y opera a nivel de subred.

¿CloudWatch y CloudTrail?

CloudWatch observa métricas, logs y alarmas; CloudTrail registra actividad de API para auditoría e investigación.

¿Qué hace Auto Scaling?

Ajusta la capacidad de un grupo conforme a políticas y métricas; necesita límites, health checks y capacidad disponible.

¿Cómo aseguras una cuenta AWS?

MFA/federación para humanos, roles con credenciales temporales para workloads, permisos mínimos, separación de cuentas, logging, cifrado y seguimiento de costos.

¿Qué es una subred pública?

Una subred con una ruta apropiada hacia un Internet Gateway; para acceso real también importan direcciones, reglas de red y configuración del recurso.

¿Cómo investigar AccessDenied?

Identifica acción y ARN; inspecciona IAM policies, resource policy, SCP, permissions boundary, session policy y condiciones. No soluciones adjuntando AdministratorAccess como primer paso.

¿Qué es IaC?

Definir infraestructura mediante archivos versionados y revisables; Terraform y CloudFormation permiten planificar/revisar cambios antes de aplicar.

¿Cómo reduces costo?

Mide consumo, dimensiona recursos, elimina huérfanos, revisa retención/transferencia y usa presupuestos; valida el impacto antes de tocar producción.

Microsoft Azure

Azure reúne infraestructura, plataformas, identidad, datos y servicios de operación. Para cada recurso estudia su modelo de red, identidad, alta disponibilidad, gobernanza y costo.

Compute Networking Identity Data

Conceptos, herramientas y ejemplos

Cómputo y aplicaciones

Virtual Machines ofrece máquinas virtuales; App Service simplifica despliegues web compatibles; Azure Functions ejecuta funciones disparadas por eventos; AKS ofrece Kubernetes administrado.

Redes

Virtual Network y subnets organizan la conectividad; NSG filtra tráfico; Load Balancer y Application Gateway cumplen funciones distintas. Revisa rutas, DNS, private endpoints y reglas efectivas al diagnosticar.

Almacenamiento y datos

Blob Storage es almacenamiento de objetos; Azure Files ofrece archivos compartidos; Managed Disks sirven como almacenamiento de bloques; Azure SQL y Cosmos DB cubren modelos de datos distintos.

Identidad y gobierno

Microsoft Entra ID administra identidad; Azure RBAC controla el acceso a recursos; Policy evalúa o restringe configuraciones; Key Vault protege secretos y claves. Distingue roles de directorio de roles de recursos Azure.

CLOUD ARCHITECTURE

Arquitectura Cloud

Convierte requisitos de negocio en decisiones técnicas explícitas: disponibilidad, seguridad, rendimiento, costo, operación y sostenibilidad.

Conceptos, herramientas y ejemplos

Diseño multi-AZ

Distribuye componentes que deben tolerar la caída de una zona; confirma que los servicios y datos soporten réplica y failover. Diseña pruebas de conmutación y documenta dependencias.

Red de tres capas

Patrón frecuente: subred pública para componentes de entrada, subred privada para aplicación y capa de datos con acceso restringido. No es una regla universal; la topología depende de los controles requeridos.

Diseño stateless y stateful

Las capas stateless pueden replicarse con menor coordinación; el estado persistente debe almacenarse en servicios adecuados y diseñarse con consistencia, backup y recuperación.

Arquitectura basada en eventos

Colas y buses de eventos desacoplan productores y consumidores. Diseña idempotencia, reintentos, DLQ, observabilidad y orden de mensajes si aplica.

Trade-offs

No existe una arquitectura “mejor” en abstracto. Justifica decisiones con requisitos, capacidad operativa, riesgo, latencia, costo y facilidad de recuperación.

Preguntas frecuentes y de entrevista

¿Por qué usar varias zonas?

Para reducir el impacto de fallos localizados; debe complementarse con rutas de failover, capacidad, datos replicados y pruebas.

¿Cuándo elegir monolito o microservicios?

Un monolito modular suele simplificar operación al inicio; microservicios convienen cuando límites de dominio, despliegue independiente y escalado compensan la complejidad distribuida.

¿Qué es una arquitectura resiliente?

Una diseñada para degradarse de forma controlada, detectar fallos y recuperarse mediante redundancia, timeouts, retries con backoff, circuit breakers y recuperación probada.

Seguridad en Cloud

FinOps y optimización de costos

Dimensionamiento

DEVOPS CULTURE & PRACTICE

Fundamentos de DevOps

DevOps conecta desarrollo y operación mediante colaboración, automatización, feedback, responsabilidad compartida y mejora continua. El objetivo no es acumular herramientas, sino entregar cambios confiables de forma repetible.

Conceptos, herramientas y ejemplos

Ciclo de entrega

Planear → desarrollar → integrar → probar → empaquetar → desplegar → observar → aprender. Automatiza primero tareas repetitivas y propensas a errores; conserva puntos de aprobación para cambios de alto riesgo.

Control de versiones y colaboración

Trabaja con ramas cortas, commits claros, revisiones de código, pruebas automatizadas y trazabilidad de cambios. Evita ramas de larga vida y secretos en el repositorio.

Infraestructura reproducible

IaC, contenedores y configuración versionada reducen diferencias entre entornos. Usa revisiones de plan, state protegido, módulos reutilizables y entornos aislados.

Operación y observabilidad

Define métricas de servicio, logs útiles, alertas accionables, runbooks y procedimientos de rollback. Después del incidente, documenta aprendizajes sin buscar culpables.

DevOps vs. SRE

DevOps describe una cultura y conjunto de prácticas para mejorar el flujo de entrega y operación. SRE aplica principios de ingeniería a confiabilidad, con SLI/SLO, presupuestos de error y automatización.

Preguntas frecuentes y de entrevista

¿DevOps es un cargo o una cultura?

Es principalmente un conjunto de prácticas y principios; los cargos llamados DevOps Engineer suelen implementar automatización, CI/CD, infraestructura y operación.

¿Qué debe automatizarse primero?

Tareas repetitivas, deterministas y con alto riesgo de error manual: validaciones, pruebas, builds, despliegues rutinarios, backups verificados y comprobaciones operativas.

¿Qué es un rollback?

Volver a una versión/configuración conocida como buena. No siempre es trivial si hay cambios de datos o esquemas irreversibles.

¿Cómo medir una mejora DevOps?

Tiempo de entrega, frecuencia de despliegue, tasa de fallos de cambio, tiempo de recuperación y medidas de calidad propias del servicio.

VERSION CONTROL

Git y GitHub

Git registra cambios en un repositorio distribuido; GitHub añade alojamiento, colaboración, pull requests, issues y automatización.

Conceptos, herramientas y ejemplos

Flujo básico

git status muestra el estado; git add prepara; git commit registra localmente; git pull integra cambios remotos y git push publica commits. Inspecciona el diff antes de confirmar.

Branches y pull requests

Crea ramas pequeñas por tarea, abre un PR con contexto, pruebas y riesgos, solicita revisión y fusiona según la política del equipo. Mantén la rama al día para resolver conflictos pronto.

Merge vs. rebase

Merge integra historias y puede crear un commit de merge. Rebase reaplica commits sobre otra base y crea nuevos hashes; evita reescribir historial público compartido sin coordinación.

Resolver un conflicto

Identifica marcadores <<<<<<< , decide la versión correcta, elimina marcadores, ejecuta pruebas y completa la operación con add/continue según merge o rebase.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

git status
git diff
git add src/
git commit -m "Documenta flujo de despliegue"
git fetch origin
git log --oneline --graph --decorate -12

Errores frecuentes y diagnóstico

No puedo hacer push

Comprueba remoto, autenticación, permisos, rama de destino, protección de ramas y si el repositorio remoto avanzó. Usa fetch y revisa el historial antes de forzar un push.

Merge conflict

Entiende ambos cambios; no reemplaces todo el archivo automáticamente. Resuelve, prueba y verifica el diff final antes de confirmar.

Preguntas frecuentes y de entrevista

¿Git y GitHub son lo mismo?

No. Git es el sistema de control de versiones; GitHub es una plataforma que aloja repositorios Git y herramientas de colaboración.

¿Qué diferencia hay entre fetch y pull?

Fetch descarga refs y objetos sin integrar los cambios a la rama actual; pull normalmente ejecuta fetch y después merge o rebase según configuración.

¿Cómo deshago un commit ya publicado?

Para historia compartida, suele preferirse <code>git revert</code> para crear un commit inverso. Reset reescribe la rama y debe usarse con cuidado.

¿Qué no debe subirse al repositorio?

Tokens, contraseñas, claves privadas, datos personales o artefactos generados grandes/sensibles. Si un secreto se filtró, revócalo; borrarlo del último commit no basta.

GitHub Actions

GitHub Actions ejecuta workflows definidos en YAML cuando ocurren eventos del repositorio, por horario o por disparadores manuales.

Conceptos, herramientas y ejemplos

Anatomía del workflow

Un workflow contiene on , jobs , runs-on y steps . Un step puede ejecutar comandos o llamar a una action. Usa permisos explícitos y fija versiones confiables.

Secretos y permisos

Guarda credenciales en el gestor de secrets o emplea OIDC/federación hacia la nube cuando sea compatible. Asigna permissions mínimos al token GITHUB_TOKEN y evita imprimir valores secretos.

Artefactos y entornos

Separa build, test y deploy; conserva artefactos que necesites promover entre fases. Usa environments y aprobaciones para despliegues sensibles, sin recompilar versiones distintas después de validarlas.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

name: Validate site
on:
  push:
  pull_request:
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check required files
        run: test -f index.html && test -f style.css && test -f script.js

Errores frecuentes y diagnóstico

Permission denied

El token no tiene permiso suficiente, el entorno tiene aprobación pendiente o el role federado no confía en la identidad del workflow. Reduce el alcance del diagnóstico a la acción que falla.

Preguntas frecuentes y de entrevista

¿Qué diferencia hay entre job y step?

Un job es una unidad de ejecución en un runner; sus steps se ejecutan en secuencia. Jobs diferentes pueden ejecutarse en paralelo o depender de otros mediante needs.

¿Cómo despliego una página de GitHub Pages?

Configura la fuente de publicación y los permisos del workflow; valida que la ruta de publicación incluya los archivos del sitio y revisa logs si falla.

¿Cómo accede un workflow a AWS?

Preferiblemente usa OIDC y un role con trust policy y permisos mínimos, evitando claves de larga duración almacenadas como secrets cuando sea posible.

¿Por qué falla una action que funcionaba?

Inspecciona los logs, versiones de actions, cambios de runtime, permisos, paths, variables, secretos y disponibilidad de servicios.

GitLab CI/CD

GitLab CI/CD define pipelines en `.gitlab-ci.yml`; los runners ejecutan los trabajos y los artifacts/cache ayudan a pasar resultados entre etapas.

Conceptos, herramientas y ejemplos

Stages y jobs

Stages ordenan fases del pipeline; jobs son trabajos ejecutables, condicionados mediante rules/needs y ejecutados por runners. Los jobs de una misma fase pueden paralelizarse según dependencias.

Artifacts y cache

Artifacts conservan resultados para fases posteriores o descarga; cache acelera dependencias repetibles. No uses cache como almacenamiento fiable del único artefacto de release.

Variables y environments

Usa variables protegidas/enmascaradas y scopes adecuados. Para despliegues, define entornos, reglas y aprobaciones; limita runner privileges y evita shells privilegiados sin necesidad.

stages:

test_site:
  stage: test
  script:
    - test -f index.html
    - test -f style.css
    - test -f script.js

¿Qué es un runner?

Agente que ejecuta jobs de CI/CD en el entorno configurado.

¿Qué diferencia hay entre artifacts y cache?

Artifacts guardan salidas que se necesitan publicar o pasar; cache acelera tareas reutilizando dependencias.

¿Cómo protejo las credenciales?

Utiliza variables masked/protected o integración de secretos, limita su scope y no las imprimas en logs.

Pipelines y despliegues CI/CD

CI/CD automatiza validaciones y la promoción de cambios. Un pipeline confiable produce artefactos trazables, ejecuta pruebas y despliega con controles.

Conceptos, herramientas y ejemplos

CI: integración continua

Integra cambios pequeños con frecuencia, compila y ejecuta pruebas rápidas en cada cambio. La señal debe llegar pronto y bloquear una integración defectuosa.

Continuous Delivery vs. Deployment

Continuous Delivery mantiene una versión validada lista para liberar y puede requerir aprobación. Continuous Deployment lleva automáticamente cambios que superan la política hasta producción.

Estrategias de despliegue

Rolling actualiza progresivamente; blue-green cambia entre dos entornos; canary habilita tráfico gradual. Todas requieren métricas, criterio de avance y rollback claro.

Promoción de artefactos

Construye una vez y promueve el mismo artefacto por entornos. Firma/escanea artefactos cuando proceda y asocia versión, commit, pruebas y aprobaciones.

Preguntas frecuentes y de entrevista

¿Qué diferencia hay entre CI y CD?

CI integra y valida cambios; CD puede referirse a entrega continua o despliegue continuo. Explica si el último salto a producción necesita aprobación.

¿Cómo manejar una migración de base de datos?

Planifica compatibilidad hacia atrás, migraciones aditivas, backups y ventana de rollback; separar despliegue de código y cambios destructivos reduce riesgo.

¿Qué es un deployment gate?

Condición para continuar una liberación, por ejemplo tests, escaneo, aprobación o métrica de salud.

¿Qué medir en un pipeline?

Duración, tasa de éxito, frecuencia de despliegue, fallos de cambio, flakiness de tests y tiempo de recuperación.

DECLARATIVE OPERATIONS

GitOps

GitOps mantiene en Git la configuración declarativa deseada y usa un controlador para reconciliar el estado real, especialmente en entornos cloud-native.

Conceptos, herramientas y ejemplos

Estado deseado y reconciliación

El repositorio expresa el estado declarativo; el reconciler detecta drift y aplica cambios autorizados. Git aporta review, historial y rollback del manifiesto, pero no reemplaza backups de datos.

Pull-based vs push-based

Un enfoque pull-based permite que el clúster consulte la fuente declarativa, reduciendo la necesidad de credenciales de despliegue externas con acceso al clúster. La seguridad depende del modelo completo.

Promoción entre entornos

Separa parámetros de desarrollo, staging y producción mediante overlays/valores y revisiones controladas. Evita secretos en texto plano y valida manifests en CI.

Preguntas frecuentes y de entrevista

¿GitOps es igual a CI/CD?

No. CI/CD automatiza pruebas y entrega; GitOps se centra en reconciliar el estado del entorno a partir de configuración declarativa versionada.

¿Qué es drift?

Diferencia entre estado declarado y real. Investiga si fue un cambio manual o una reconciliación; corrige la fuente de verdad antes de forzar cambios peligrosos.

¿GitOps significa que todo debe estar en Git?

La configuración declarativa puede estar versionada; secretos reales, datos runtime y estado mutable requieren tratamiento especializado.

RELIABILITY ENGINEERING

Site Reliability Engineering (SRE)

SRE aplica ingeniería al trabajo operacional: define objetivos mensurables, automatiza tareas repetitivas y trata la confiabilidad como una propiedad diseñada.

Conceptos, herramientas y ejemplos

SLI, SLO y SLA

SLI es el indicador medido; SLO es el objetivo interno para ese indicador; SLA es un acuerdo con compromisos y consecuencias. Define ventanas y población de medición con claridad.

Error budget

Presupuesto de error representa el margen de incumplimiento compatible con un SLO. Cuando se agota, el equipo puede priorizar confiabilidad en vez de nuevas liberaciones según su política.

Alertas útiles

Alerta sobre síntomas que afectan al usuario y requieren acción, con umbrales/ventanas que reduzcan ruido. Cada alerta crítica necesita propietario, contexto y procedimiento de respuesta.

Postmortem sin culpa

Documenta impacto, línea temporal, causas contribuyentes, detección, recuperación y acciones con responsables/fechas. Evita concluir que el incidente se explica solo por “error humano”.

Preguntas frecuentes y de entrevista

¿Qué diferencia hay entre monitorización y observabilidad?

Monitorización suele comprobar señales conocidas y alertar; observabilidad permite investigar estados internos a partir de métricas, logs, trazas y contexto.

¿Qué es toil?

Trabajo operacional repetitivo, manual, automatizable y que crece con el servicio. Reducirlo libera capacidad para ingeniería.

¿Por qué no fijar siempre 100% de disponibilidad?

Un objetivo absoluto puede ser inalcanzable o excesivamente costoso; el SLO debe reflejar necesidades del usuario y trade-off de costo/velocidad.

Contenedores y orquestación

Los contenedores empaquetan una aplicación con sus dependencias. La orquestación coordina réplicas, disponibilidad, networking, configuración y despliegue en múltiples nodos.

Conceptos, herramientas y ejemplos

Imagen vs. contenedor

Una imagen contiene capas y metadatos para crear instancias; un contenedor es un proceso aislado que se ejecuta a partir de una imagen. Los datos persistentes deben guardarse en volúmenes o servicios externos apropiados.

Registry y versionado

Un registry distribuye imágenes. Etiqueta builds con versiones trazables y, cuando corresponda, utiliza digests inmutables en producción. Escanea imágenes y evita incluir secretos en capas.

¿Cuándo usar Kubernetes?

Kubernetes ofrece reconciliación, scheduling, servicios y despliegues declarativos, pero añade complejidad. Para una aplicación pequeña puede bastar una plataforma de contenedores administrada más simple.

Seguridad de contenedores

Ejecuta como usuario no root, usa imágenes mínimas, limita capabilities, configura límites de recursos, escanea dependencias y separa secretos del image build.

Preguntas frecuentes y de entrevista

¿Los contenedores sustituyen a las máquinas virtuales?

No necesariamente. Comparten el kernel del sistema anfitrión y aíslan procesos; las VMs virtualizan sistemas operativos completos. Se pueden usar juntos.

¿Dónde se guardan los datos de un contenedor?

En su filesystem escribible, pero ese contenido no debe asumirse persistente al reemplazarlo. Usa volúmenes o almacenamiento externo para datos que deben sobrevivir.

¿Por qué funciona localmente pero no en producción?

Compara variables, arquitectura de CPU, permisos, puertos, DNS, mounts, versiones y límites de recursos; reproduce el entorno y consulta logs.

CONTAINER TOOLING

Docker

Docker construye imágenes y ejecuta contenedores. Separa build, configuración de runtime, datos persistentes y red para crear despliegues repetibles.

Conceptos, herramientas y ejemplos

Dockerfile y capas

Usa una imagen base adecuada, copia primero manifiestos de dependencias para aprovechar cache, fija versiones, ejecuta como usuario no root y excluye archivos locales mediante .dockerignore.

Puertos, redes y volúmenes

-p host:container publica un puerto; las redes conectan servicios; volúmenes conservan datos. Publicar un puerto no configura automáticamente firewall, TLS ni autenticación.

Logs y diagnóstico

docker ps -a , docker logs , docker inspect y docker exec permiten inspeccionar estado, salida, configuración y procesos dentro de un contenedor.

Build reproducible

Evita tags ambiguos en entornos importantes; controla build context, dependencias, arquitectura, variables de build y escaneo de vulnerabilidades. No pases secretos mediante ARG o layers ordinarios.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

docker build -t demo-app:1.0 .
docker run --rm --name demo-app -p 8080:80 demo-app:1.0
docker ps -a
docker logs demo-app
docker inspect demo-app
docker stop demo-app

Errores frecuentes y diagnóstico

Puerto ocupado

Comprueba el puerto usado en el host y el mapping con docker ps ; cambia el puerto de host o detén el proceso dueño si corresponde.

Contenedor en bucle de reinicio

Revisa logs, healthcheck, variable/secretos requeridos y dependencia no disponible. Evita reinicios sin diagnóstico.

Preguntas frecuentes y de entrevista

¿Imagen o contenedor?

La imagen es una plantilla versionada; el contenedor es la instancia ejecutable.

¿Qué hace EXPOSE?

Documenta el puerto previsto de la imagen, pero por sí solo no publica el puerto en el host.

¿Para qué sirve .dockerignore?

Excluye del build context archivos que no deben copiarse o enviarse, como .git, caches, archivos locales o secretos.

¿Por qué un contenedor termina inmediatamente?

Su proceso principal terminó o falló. Revisa exit code, logs, CMD/ENTRYPOINT y configuración.

¿Cómo se persisten datos?

Mediante volúmenes o almacenamiento externo; no dependas del filesystem efímero del contenedor para datos críticos.

CONTAINER ORCHESTRATION

Kubernetes

Kubernetes mantiene el estado deseado de aplicaciones declaradas mediante objetos API. Además de conocer kubectl, comprende scheduling, networking, probes, RBAC, escalado y troubleshooting.

Conceptos, herramientas y ejemplos

Pod, Deployment y Service

Pod es la unidad de ejecución básica; Deployment gestiona réplicas y rollouts para workloads stateless; Service proporciona descubrimiento y acceso estable a un conjunto de pods.

ConfigMap, Secret y probes

ConfigMap configura aplicaciones; Secret almacena datos sensibles como objeto API, pero necesita controles de RBAC y protección del clúster. Readiness determina si el pod recibe tráfico; liveness ayuda a detectar procesos que necesitan reinicio; startup probe protege inicialización lenta.

Ingress, Gateway y NetworkPolicy

Ingress expone rutas HTTP mediante un controller; Gateway API ofrece recursos modernos de networking compatibles con implementaciones. NetworkPolicy segmenta tráfico de pods si el plugin de red la implementa.

Requests, limits y HPA

Requests influyen en scheduling; limits acotan consumo compatible; HPA ajusta réplicas a métricas. Límites mal ajustados pueden provocar throttling u OOMKilled.

RBAC y contexto de kubectl

Role/ClusterRole definen permisos; RoleBinding/ClusterRoleBinding asignan esos permisos. Revisa contexto y namespace antes de ejecutar cambios; usa permisos mínimos.

Helm

Helm empaqueta plantillas, defaults y metadatos en charts. Versiona values y revisa el manifiesto renderizado; no des por seguro un chart de terceros sin revisar origen, permisos e imágenes.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

kubectl config current-context
kubectl get pods -A
kubectl describe pod POD -n NAMESPACE
kubectl logs POD -n NAMESPACE --previous
kubectl get events -n NAMESPACE --sort-by=.lastTimestamp
kubectl apply --dry-run=server -f deployment.yaml

Errores frecuentes y diagnóstico

ImagePullBackOff

Verifica nombre/tag/digest, permisos del registry, pull secret, conectividad y compatibilidad de la imagen.

Pending

Revisa describe y eventos: recursos insuficientes, afinidad/taints, PVC sin bind, restricciones de scheduling o nodos no disponibles.

Service sin tráfico

Comprueba selector y labels, endpoints, puerto/targetPort, readiness probe, NetworkPolicy, Ingress/Gateway y logs del backend.

Preguntas frecuentes y de entrevista

¿Pod y Deployment son iguales?

No. Pod ejecuta contenedores; Deployment controla el rollout y réplicas mediante ReplicaSets para una aplicación compatible.

¿Readiness y liveness?

Readiness decide si el pod debe recibir tráfico; liveness detecta procesos no saludables que pueden necesitar reinicio.

¿Cómo diagnostico CrashLoopBackOff?

Describe pod, revisa eventos y logs actuales/previous, comando/args, variables, Secret, permisos, probes y consumo de recursos.

¿Qué hace Service?

Proporciona nombre/IP virtual estable y selecciona pods mediante labels/selector para permitir comunicación.

¿Cómo limitar acceso al clúster?

RBAC mínimo, identidad federada cuando proceda, acceso API restringido, auditing y protección de secretos.

Infraestructura como código

IaC representa infraestructura como archivos que se pueden revisar, probar, versionar y aplicar de manera repetible.

Conceptos, herramientas y ejemplos

Declarativo vs imperativo

Declarativo expresa el estado final esperado; imperativo describe pasos. Ambos pueden coexistir, pero mezclar cambios manuales con IaC sin reconciliación suele generar drift.

State, plan y apply

En Terraform, state registra la relación entre configuración y recursos; plan anticipa cambios; apply ejecuta cambios autorizados. Guarda state en backend protegido y coordina accesos concurrentes.

Módulos y entornos

Reutiliza módulos con interfaces claras. Separa variables por entorno, limita defaults peligrosos y evita duplicación descontrolada. Revisa permisos y costes del plan antes de aplicar.

Escanea configuraciones, protege secretos y state, revisa políticas de red/IAM y requiere aprobación para cambios críticos. El plan también puede mostrar valores sensibles según configuración.

¿Qué diferencia hay entre provisioning y configuration management?

Provisioning crea recursos como redes y máquinas; configuration management instala y mantiene el estado del software/configuración. Herramientas pueden cubrir varias funciones.

Diferencia entre estado esperado y real, por cambios manuales o externos. Comprueba el plan y reconcilia la fuente de verdad con cuidado.

¿Por qué proteger el state?

Puede contener identificadores, atributos y datos sensibles. Usa control de acceso, cifrado, locking cuando aplique y backups.

¿Cómo revisar un cambio antes de ejecutar?

Valida sintaxis, analiza plan/diff, permisos, destrucciones, exposición pública, coste e impacto operacional; usa revisión por pares para cambios importantes.

Terraform

Terraform define infraestructura con HCL y providers. La secuencia habitual es init → fmt/validate → plan → revisión → apply, con state y credenciales gestionadas cuidadosamente.

Conceptos, herramientas y ejemplos

Providers, resources y data sources

Provider configura integración con una plataforma; resource declara recursos administrados; data source consulta información existente. Fija versiones compatibles y revisa lockfile.

Variables, outputs y módulos

Variables parametrizan configuración; outputs publican valores necesarios; módulos agrupan recursos. Diseña interfaces pequeñas y valida input en vez de copiar bloques masivos entre entornos.

Remote state y locking

Un backend remoto facilita colaboración y puede proteger concurrencia con locking compatible. Restringe acceso y encripta; no guardes state en repositorios públicos.

Import, moved y drift

Import asocia recursos ya existentes con Terraform; moved declara movimientos de direcciones; el plan detecta divergencias. Lee la documentación de la versión para la sintaxis y workflow concretos.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

terraform fmt -recursive
terraform init
terraform validate
terraform plan -out=tfplan
terraform show tfplan
# Después de revisar el plan:
terraform apply tfplan

Errores frecuentes y diagnóstico

Provider auth falla

Verifica identidad activa, variables, perfil/role, región y permisos. No copies credenciales permanentes a los archivos Terraform.

State lock

Confirma que no exista otra ejecución activa. No fuerces desbloqueo sin verificar; un desbloqueo prematuro puede corromper coordinación.

Preguntas frecuentes y de entrevista

¿Qué hace terraform init?

Inicializa el directorio y descarga providers/módulos necesarios, además de preparar el backend.

¿Qué diferencia hay entre plan y apply?

Plan muestra el cambio esperado; apply lo ejecuta. Debe revisarse el plan antes de aplicar en ambientes importantes.

¿Se debe editar state manualmente?

Normalmente no. Usa comandos de state documentados o flujos de import/move apropiados y respalda state antes de operaciones delicadas.

¿Para qué sirve un module?

Agrupa recursos y lógica reutilizable detrás de variables y outputs definidos.

¿Cómo evitar destrucciones accidentales?

Revisa el plan, usa protección/lifecycle compatible cuando corresponda, políticas y aprobaciones. Las protecciones no sustituyen un plan inspeccionado.

Credenciales de cloud, state, configuración secreta y acceso al backend del stack.

SYSTEM ADMINISTRATION

Linux

Linux es una familia de sistemas operativos central para servidores, cloud, contenedores y automatización. Aprende a inspeccionar el estado antes de cambiar servicios o permisos.

Conceptos, herramientas y ejemplos

Sistema de archivos y comandos

pwd , ls -lah , find , grep y less ayudan a navegar y localizar información. Usa rutas absolutas al automatizar tareas críticas.

Permisos y propietarios

Los permisos read/write/execute se asignan a owner, group y others. chmod modifica permisos; chown cambia propietario/grupo. Evita resolver errores aplicando chmod -R 777 .

Procesos y recursos

Usa ps , top , free , df , du y uptime para revisar CPU, RAM, disco y carga. Distingue espacio de disco del inode exhaustion.

systemd y logs

systemctl status y journalctl -u muestran estado y eventos de servicios. Antes de reiniciar, lee el error y verifica dependencias, configuración y puertos.

Paquetes y actualizaciones

Usa el gestor de paquetes de la distribución, por ejemplo apt o dnf. En producción revisa repositorios, cambios, reinicio requerido y ventana de mantenimiento.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

pwd
ls -lah
df -h
free -h
ps aux --sort=-%cpu | head
systemctl status ssh
journalctl -u ssh --since "1 hour ago"

Errores frecuentes y diagnóstico

No space left on device

Comprueba df -h e df -i , logs, archivos temporales y ficheros borrados abiertos. No borres datos arbitrariamente; identifica al propietario y retención apropiada.

Permission denied

Comprueba usuario efectivo, propietario, permisos de ruta, ACL, montaje, SELinux/AppArmor según entorno y políticas del servicio.

Preguntas frecuentes y de entrevista

¿Qué diferencia hay entre chmod y chown?

chmod cambia permisos; chown cambia propietario o grupo.

¿Cómo encuentro archivos grandes?

Usa du/ find con límites conscientes del filesystem; compara uso del filesystem con tamaño de directorios y revisa mount points.

¿Cómo diagnosticar un servicio caído?

systemctl status, journalctl, configuración, permisos, dependencias, puerto escuchando y conectividad.

¿Qué significa 755?

Owner tiene rwx; group y others tienen r-x. La interpretación exacta depende del tipo de archivo y ACL adicionales.

¿Qué diferencia hay entre df y du?

df muestra uso del filesystem; du resume uso de directorios. Archivos borrados pero aún abiertos pueden hacer que difieran.

SHELL AUTOMATION

Bash y scripting

Bash permite encadenar herramientas de sistema y automatizar rutinas. Un script seguro valida entradas, trata errores y no expone secretos.

Conceptos, herramientas y ejemplos

Variables y quoting

Usa "$var" para evitar división de palabras y expansión de glob involuntarias. Las variables de entorno sirven para configuración, pero no deberían imprimirse si contienen secretos.

Condiciones y bucles

if , case , for y while expresan decisiones y repetición. Valida los parámetros antes de realizar operaciones destructivas.

Pipes y códigos de salida

El código de salida cero suele indicar éxito. set -euo pipefail mejora detección de algunos errores, pero no reemplaza la comprensión de errores esperados, subshells y pipelines.

Tareas repetibles

Escribe logs legibles, soporta ejecución repetida cuando sea apropiado, usa rutas conocidas y permite modo dry-run para acciones de impacto.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

#!/usr/bin/env bash
set -Eeuo pipefail

if [[ $# -ne 1 ]]; then
  echo "Uso: $0 <directorio>" >&2
  exit 2
fi

target="$1"
if [[ ! -d "$target" ]]; then
  printf "No existe el directorio: %s\n" "$target" >&2
  exit 1
fi
find "$target" -type f -name "*.log" -print

Preguntas frecuentes y de entrevista

¿Por qué se cita una variable?

Para mantener el valor como un argumento y evitar división por espacios y expansión de comodines.

¿Qué hace set -euo pipefail?

Intenta hacer fallar el script ante errores no controlados, variables sin definir y fallos intermedios de pipelines; hay excepciones que deben entenderse.

¿Cómo manejar señales y limpieza?

Usa traps para limpiar archivos temporales o finalizar procesos; asegúrate de que la limpieza no oculte el error inicial.

¿Bash o Python?

Bash es conveniente para orquestar comandos de sistema; Python suele ser más mantenible para lógica compleja, parsing estructurado y tests.

LINUX OPERATIONS

Procesos y servicios

Diagnostica procesos, unidades systemd, puertos, dependencias y logs en orden. Registra la evidencia antes de reiniciar o matar procesos.

Conceptos, herramientas y ejemplos

Inspeccionar procesos

ps aux , pgrep , top y pstree muestran procesos; identifica PID, usuario, argumentos y consumo. No supongas que terminar el proceso resuelve la causa raíz.

systemd

systemctl status , start , stop , restart , enable y disable controlan unidades. Usa daemon-reload cuando cambia la definición de una unidad.

Logs y puertos

journalctl -u servicio consulta logs; ss -lntup ayuda a encontrar puertos en escucha. Verifica el proceso que ocupa un puerto antes de detenerlo.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

ps aux --sort=-%mem | head
systemctl status nginx
journalctl -u nginx -n 100 --no-pager
ss -lntup
pgrep -a nginx

Preguntas frecuentes y de entrevista

¿Proceso vs. servicio?

Proceso es un programa en ejecución; servicio es una unidad lógica de operación que frecuentemente se administra con systemd.

¿Qué hace systemctl enable?

Configura el servicio para iniciarse automáticamente conforme a la unidad y targets definidos; no equivale necesariamente a iniciarlo inmediatamente.

¿Cómo reviso por qué un servicio falló al arrancar?

Consulta status, logs, archivos de configuración, permisos, dependencias y puertos; valida la configuración antes del reinicio.

REMOTE ACCESS

SSH y administración remota

SSH proporciona acceso remoto cifrado y autenticación mediante claves o mecanismos admitidos. Verifica identidad del servidor y limita acceso administrativo.

Conceptos, herramientas y ejemplos

Claves SSH

La clave privada se mantiene protegida en el cliente; la pública se instala en el servidor o sistema de identidad. Protege con passphrase y permisos de archivo apropiados.

Conexión y configuración

Usa alias en ~/.ssh/config para host, usuario, puerto y clave. Comprueba hostname, DNS, reachability, puerto, reglas de red, logs y permisos de la cuenta.

Agent forwarding y bastion

El forwarding transmite capacidad de usar agente hacia el host remoto y amplía el riesgo si ese host está comprometido. Habilítalo solo cuando sea necesario; bastions y accesos gestionados deben seguir políticas claras.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

ssh-keygen -t ed25519 -C "dev-laptop"
ssh user@host.example
ssh -v user@host.example
ssh -i ~/.ssh/id_ed25519 user@host.example

Preguntas frecuentes y de entrevista

¿La clave pública es secreta?

No, se puede distribuir; la privada debe protegerse estrictamente.

¿Qué significa REMOTE HOST IDENTIFICATION HAS CHANGED?

La clave del host cambió respecto a la guardada. Verifica por un canal confiable si hubo rotación legítima o posible suplantación antes de actualizar known_hosts.

¿Cómo depuro una conexión SSH?

Usa ssh -v; comprueba DNS/IP, puerto, firewall, clave/usuario, permisos, sshd y logs del servidor.

NETWORK ENGINEERING

Fundamentos de Networking

La resolución de problemas de red empieza por acotar origen, destino, protocolo y puerto; después se prueba cada capa del recorrido, desde DNS y rutas hasta el proceso destino.

Conceptos, herramientas y ejemplos

OSI y TCP/IP

OSI separa funciones conceptuales en siete capas; TCP/IP agrupa protocolos usados en redes reales. Sirve como mapa de diagnóstico, no como descripción exacta de cada implementación.

TCP vs. UDP

TCP ofrece flujo fiable y ordenado con control de congestión; UDP envía datagramas con menos garantías. El comportamiento requerido por la aplicación determina el protocolo.

Switching, routing y VLAN

Switching reenvía tramas dentro de una LAN; routing mueve paquetes entre redes IP; VLAN segmenta dominios de capa 2. Trunk/access y routing inter-VLAN requieren configuración coherente de ambos extremos.

DNS y DHCP

DHCP asigna configuración de red a clientes; DNS resuelve nombres y otros registros. Un problema DNS puede parecer fallo de conectividad aunque la IP destino sea accesible.

HTTP, TLS y puertos

Comprueba resolución, ruta, TCP handshake, TLS/certificados y después la respuesta HTTP. Un puerto abierto no demuestra que la aplicación responda correctamente.

Preguntas frecuentes y de entrevista

¿Qué ocurre al abrir una página web?

Simplificando: resolución DNS, establecimiento de transporte (TCP o QUIC/UDP según protocolo), negociación TLS si es HTTPS, solicitud HTTP, respuesta y renderizado; caché, proxies y CDN pueden cambiar el recorrido.

¿Ping garantiza que una aplicación funciona?

No. ICMP puede estar bloqueado aunque el servicio funcione; y responder a ping no confirma que el puerto o la aplicación específica estén sanos.

¿Qué diferencia hay entre switch y router?

Switch conecta segmentos de capa 2; router reenvía tráfico entre redes de capa 3, según sus rutas.

¿Qué es NAT?

Traducción de direcciones o puertos entre espacios de red; puede permitir conectividad saliente o publicar servicios según tipo y reglas.

¿Qué diferencia hay entre latencia y ancho de banda?

Latencia mide el tiempo que tarda una señal/solicitud; ancho de banda representa capacidad de transmisión. Un enlace puede tener gran ancho de banda y aun así latencia alta.

¿Qué causa una resolución DNS incorrecta?

Registros o delegación erróneos, caché/TTL, resolvers, split DNS, hosts locales o cambios que aún no han propagado según TTL.

IP, CIDR y subnetting

CIDR representa una red indicando cuántos bits pertenecen al prefijo. Calcula rango, broadcast (IPv4 tradicional), hosts y solapamiento antes de definir una VPC o subnet.

Conceptos, herramientas y ejemplos

Ejemplo resuelto: /24

Red 192.168.10.0/24 : máscara 255.255.255.0 , 256 direcciones totales, rango tradicional de hosts 192.168.10.1–192.168.10.254 y broadcast 192.168.10.255 . En redes cloud algunos rangos reservan direcciones; consulta el proveedor.

Ejemplo resuelto: /26

Una IPv4 /26 tiene 64 direcciones y máscara 255.255.255.192 . Los bloques avanzan de 64 en el último octeto: .0, .64, .128 y .192. En el bloque .64/26, el broadcast tradicional es .127 y hosts .65–.126.

Planificar subredes

Lista cantidad de hosts, crecimiento, zonas, rutas, gateways y servicios reservados. Evita rangos que se solapen con la red corporativa, VPN u otras redes conectadas.

IPv6

IPv6 usa direcciones de 128 bits y notación hexadecimal comprimida. No tiene broadcast; utiliza multicast y mecanismos como Neighbor Discovery. No supongas que una red IPv6 tiene el mismo modelo de NAT que IPv4.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

ip addr
ip route
ip -6 route
# Ver máscara y rango de una red en laboratorio:
ipcalc 192.168.10.64/26

Preguntas frecuentes y de entrevista

¿Qué significa /24?

Que 24 bits forman el prefijo de red; quedan 8 bits en la parte de host en IPv4.

¿Cuántas direcciones tiene una /26?

2^(32−26) = 64 direcciones totales; en una LAN IPv4 convencional suelen descontarse dirección de red y broadcast para hosts.

¿Qué es CIDR?

Notación de prefijo que permite representar bloques IP con longitud variable, facilitando sumarización y asignación flexible.

¿Qué es una ruta por defecto?

Ruta usada cuando no existe una ruta más específica para el destino, frecuentemente indicada como 0.0.0.0/0 para IPv4.

¿Por qué evitar rangos solapados en VPN?

Enrutamiento se vuelve ambiguo y dificulta la comunicación entre redes; suele requerir renumeración o traducción cuidadosamente diseñada.

NETWORK SERVICES

DNS y DHCP

DNS traduce nombres a registros consultables; DHCP asigna parámetros de red. Ambos influyen en conectividad y deben comprobarse por separado.

Conceptos, herramientas y ejemplos

Tipos de registros DNS

A/AAAA vinculan nombre con IP; CNAME crea un alias; MX señala servidores de correo; TXT transporta información de texto utilizada por varios servicios; NS delega servidores autoritativos. Respeta restricciones por tipo de registro.

Recursión y autoridad

Un resolver recursivo busca respuestas para el cliente; servidores autoritativos publican los registros de una zona. TTL controla cuánto tiempo se puede cachear una respuesta.

DHCP DORA

El flujo típico Discover, Offer, Request, Acknowledge permite al cliente obtener una concesión. Revisa scope agotado, VLAN, relay, lease, gateway y DNS entregados.

Diagnóstico práctico

Compara resolución desde distintos resolvers, revisa registros autoritativos, TTL y caché local. Si una IP funciona pero el hostname no, prioriza DNS; si falla todo, continúa por rutas y puertos.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

dig example.com A
dig example.com AAAA
dig +short example.com
nslookup example.com
# Linux systemd resolver, cuando esté instalado:
resolvectl status

Preguntas frecuentes y de entrevista

¿Qué es TTL?

Tiempo durante el cual una respuesta puede mantenerse cacheada según sus reglas.

¿CNAME o A?

A apunta a una IPv4; CNAME indica alias a otro nombre. La compatibilidad con otros registros depende de la zona y proveedor DNS.

¿Qué ocurre si el DHCP se agota?

Nuevos clientes pueden no obtener una dirección; inspecciona tamaño del scope, leases, VLAN/relay y dispositivos que retienen direcciones.

¿Cambiar DNS resuelve un fallo TCP?

No necesariamente. DNS soluciona la resolución de nombres; después debe existir ruta, acceso al puerto y una aplicación saludable.

NETWORK ENGINEERING

Routing, NAT y VLAN

Estos mecanismos separan dominios de red y determinan por dónde circulan los paquetes. Verifica las rutas de ida y retorno: que un lado conozca el destino no garantiza el camino inverso.

Conceptos, herramientas y ejemplos

Rutas y longest-prefix match

El router suele escoger la ruta coincidente más específica. Una ruta por defecto se utiliza si no existe una más específica; también importan métrica, protocolo y política de enrutamiento.

NAT y PAT

NAT traduce direcciones; PAT comparte una dirección mediante puertos. NAT no sustituye firewall ni define por sí solo todos los controles de acceso.

VLAN y trunks

VLAN segmenta capa 2. Los puertos access suelen pertenecer a una VLAN; trunks transportan varias VLAN mediante etiquetas según configuración. Un mismatch de VLAN puede aislar clientes.

VPN y peering

VPN crea túneles sobre una red de tránsito; peering conecta redes según tecnología/política. Revisa rangos solapados, cifrado, rutas, MTU y controles de tráfico.

Preguntas frecuentes y de entrevista

¿Qué es una ruta estática?

Ruta configurada manualmente; es simple pero requiere mantenimiento si cambia la topología.

¿Qué significa asymmetric routing?

El tráfico de ida y vuelta toma caminos distintos; ciertos firewalls stateful, túneles o políticas pueden fallar si no se contempla.

¿Una VLAN es una subnet?

No. VLAN segmenta capa 2; subnet representa direccionamiento capa 3. A menudo se asocian, pero no son equivalentes conceptualmente.

¿Qué comprobar en una VPN que conecta pero no comunica?

Rutas en ambos sentidos, redes permitidas, selectors, firewall, DNS, MTU y solapamientos.

NETWORK SECURITY

Firewalls, VPN y TLS

Protege comunicaciones con políticas explícitas, segmentación y cifrado. Una conexión segura necesita identidad verificada, algoritmos vigentes y gestión de claves.

Conceptos, herramientas y ejemplos

Firewall y mínimo acceso

Permite solo flujos requeridos: origen, destino, protocolo, puerto y propósito. Registra denegaciones útiles y evita reglas globales “allow any” para salir del paso.

TLS y certificados

TLS protege el canal; el cliente valida cadena de confianza, hostname, fechas y uso del certificado. Un certificado expirado o un nombre que no coincide puede romper la conexión aunque el servidor responda.

VPN

Las VPN site-to-site conectan redes; las remote-access dan acceso a usuarios. Diseña autenticación, rangos, rutas, MFA cuando aplique, split/full tunnel y revocación de acceso.

Proxy y reverse proxy

Un forward proxy actúa en nombre de clientes; un reverse proxy recibe solicitudes antes de backends y puede terminar TLS, enrutar o aplicar políticas. Ninguno reemplaza la seguridad del backend.

Preguntas frecuentes y de entrevista

¿TLS cifra también la URL?

TLS protege el contenido HTTP dentro del canal, pero ciertos metadatos de conexión pueden permanecer visibles; el alcance depende de versión y mecanismos como ECH.

¿Qué diferencia hay entre proxy y firewall?

Un proxy intermedia tráfico de aplicación; un firewall aplica políticas de acceso a tráfico. Los productos modernos pueden combinar funciones.

¿Por qué no basta con una VPN para estar seguro?

La VPN protege una parte de la ruta; aún se necesitan identidad, endpoints seguros, autorización, segmentación y control de los recursos accesibles.

NETWORK TROUBLESHOOTING

Comandos de diagnóstico de red

Usa herramientas por hipótesis: nombre, IP, ruta, puerto, TLS y aplicación. Ejecuta pruebas desde el mismo origen donde ocurre el problema y registra las diferencias.

Conceptos, herramientas y ejemplos

Conectividad y rutas

ping prueba ICMP si está permitido; traceroute / tracepath investigan saltos; ip route muestra la tabla local. El filtrado intermedio puede ocultar respuestas.

DNS y HTTP

dig consulta DNS; curl -v ayuda a observar conexión/TLS/HTTP; curl -I hace una solicitud de cabeceras, si el servidor lo admite.

Puertos y captura

ss -lntup lista sockets; nc -vz host puerto prueba conectividad TCP en instalaciones que lo soporten; tcpdump captura paquetes y debe usarse con autorización y cuidado de datos.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

dig app.example.com
curl -v https://app.example.com/
ss -lntup
ip route
tracepath app.example.com
# Captura limitada: usa interfaz y filtro adecuados
sudo tcpdump -ni eth0 host 192.0.2.10

Preguntas frecuentes y de entrevista

¿Qué indica connection refused?

Normalmente el destino es alcanzable pero no hay un servicio escuchando en ese puerto, o un dispositivo rechaza la conexión; revisa listener y reglas.

¿Qué indica timeout?

No hubo respuesta dentro del plazo; causas posibles incluyen filtrado silencioso, ruta rota, destino sin responder o pérdida de paquetes.

¿Por qué curl funciona pero el navegador no?

01. Estructura de un documento HTML

HTML (HyperText Markup Language) utiliza elementos y atributos para representar títulos, párrafos, enlaces, imágenes, formularios y otras partes del contenido. El navegador interpreta el documento y construye el DOM.

Plantilla mínima y función de cada parte 
<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <meta name="description" content="Descripción de la página">
    <title>Mi página</title>
    <link rel="stylesheet" href="./style.css">
    <script src="./script.js" defer></script>
</head>
<body>
    <header>
        <h1>Título principal</h1>
    </header>
    <main>
        <p>Contenido principal de la página.</p>
    </main>
</body>
</html>
  • <!DOCTYPE html> : activa el modo estándar de renderizado.
  • <html lang="es"> : declara el idioma principal del documento.
  • <head> : contiene metadatos, título, referencias a estilos y recursos.
  • charset : define la codificación de caracteres, normalmente UTF-8.
  • viewport : ayuda a adaptar el ancho del documento a la pantalla del dispositivo.
  • defer : permite descargar el JavaScript en paralelo y ejecutarlo después de analizar el HTML.
  • <main> : agrupa el contenido principal de la página.
Elementos, etiquetas, atributos y anidamiento

Una etiqueta es la marca escrita entre los signos angulares; un elemento incluye la etiqueta, su contenido y, cuando corresponda, la etiqueta de cierre. Los atributos añaden información o configuración al elemento. 

<a href="https://developer.mozilla.org/" target="_blank" rel="noopener noreferrer">
    Consultar documentación
</a>

href , target y rel son atributos. Los elementos deben anidarse correctamente; no se debe cerrar un elemento fuera del orden en el que se abrió.

Consejo: utiliza nombres de atributos entre comillas y evita atributos obsoletos de presentación, como align . La presentación corresponde a CSS.

Títulos, párrafos, listas y enlaces 
<h1>Tema principal</h1>
<h2>Subtema</h2>
<p>Un párrafo explicativo.</p>

<ul>
    <li>Elemento sin orden numérico</li>
    <li>Otro elemento</li>
</ul>

<ol>
    <li>Primer paso</li>
    <li>Segundo paso</li>
</ol>

<a href="/contacto/">Ir a contacto</a>

Usa los encabezados en una jerarquía lógica para organizar el contenido. No elijas h2 o h3 únicamente porque su tamaño visual te gusta: los tamaños se controlan con CSS.

Para enlaces que abren otra pestaña con target="_blank" , utiliza rel="noopener noreferrer" . El texto del enlace debe explicar el destino siempre que sea posible.

Imágenes, audio, vídeo y rutas de recursos 
<img
    src="./img/diagrama-red.png"
    alt="Diagrama de una red con tres subredes"
    width="960"
    height="540"
>

<video controls width="720" poster="./img/portada.jpg">
    <source src="./media/demo.mp4" type="video/mp4">
    Tu navegador no admite este vídeo.
</video>

El texto alternativo ( alt ) debe describir la información relevante de la imagen. Si la imagen es puramente decorativa, utiliza alt="" . Evita textos alternativos como “imagen de” cuando no aportan información.

En GitHub Pages, revisa rutas relativas y mayúsculas/minúsculas: una ruta que funciona localmente en Windows puede fallar en el servidor si el nombre no coincide exactamente.

02. HTML semántico y accesibilidad

La semántica comunica el propósito de cada región del documento a navegadores, tecnologías de asistencia, motores de búsqueda y otros desarrolladores. Un HTML semántico suele ser más fácil de mantener que una página formada solo por contenedores genéricos.

Cuándo usar header, nav, main, section, article, aside y footer
  • header : cabecera de una página o de una sección.
  • nav : bloque de navegación principal o secundaria.
  • main : contenido principal único de la página.
  • section : agrupación temática de contenido, normalmente con encabezado.
  • article : contenido independiente o reutilizable, como una publicación o una ficha autónoma.
  • aside : contenido complementario al contenido principal.
  • footer : información de cierre de una página o sección.
  • div : contenedor genérico cuando no existe un elemento semántico más apropiado. 
<body>
    <header>...</header>
    <nav aria-label="Principal">...</nav>
    <main>
        <article>
            <h1>Título del artículo</h1>
            <section>
                <h2>Primer apartado</h2>
                <p>Contenido...</p>
            </section>
        </article>
        <aside>Contenido relacionado</aside>
    </main>
    <footer>...</footer>
</body>
Etiquetas y atributos útiles para accesibilidad
  • Asocia cada campo de formulario con un <label> mediante for e id .
  • Usa el atributo alt de acuerdo con el propósito de cada imagen.
  • Asegura un orden lógico de encabezados y una estructura navegable.
  • Haz que los controles interactivos funcionen con teclado y mantén visible el foco.
  • Usa nombres accesibles para iconos y controles sin texto visible.
  • Elige contraste suficiente entre texto y fondo; no dependas solamente del color para comunicar un estado. 
<label for="correo">Correo electrónico</label>
<input id="correo" name="correo" type="email" autocomplete="email" required>

<button type="button" aria-label="Cerrar menú">
    <span aria-hidden="true">×</span>
</button>

ARIA complementa la semántica nativa cuando hace falta; no sustituye un elemento HTML correcto. Un botón real suele ser preferible a un div con un evento de clic.

DOM, atributos id y class

El DOM (Document Object Model) representa el documento como un árbol que JavaScript puede consultar y modificar. El atributo id identifica un elemento concreto dentro del documento; class permite agrupar elementos para aplicar estilos o comportamiento compartido. 

<section id="servicios" class="panel panel-cloud">
    <h2 class="panel-title">Servicios cloud</h2>
</section>

Buenas prácticas: mantén los id únicos, utiliza nombres de clase descriptivos y no uses identificadores duplicados para intentar aplicar el mismo estilo a varios elementos.

03. Formularios y datos de entrada

Los formularios permiten recoger información y enviarla al destino configurado. HTML ofrece controles nativos y validación básica en el navegador; la validación del cliente mejora la experiencia, pero el servidor debe validar de nuevo los datos.

Tipos de input y atributos habituales 
<form action="/registro" method="post">
    <label for="nombre">Nombre</label>
    <input id="nombre" name="nombre" type="text" required minlength="2">

    <label for="email">Correo</label>
    <input id="email" name="email" type="email" required autocomplete="email">

    <label for="nivel">Nivel</label>
    <select id="nivel" name="nivel">
        <option value="junior">Junior</option>
        <option value="intermedio">Intermedio</option>
    </select>

    <button type="submit">Enviar</button>
</form>
  • text : texto general.
  • email : entrada con comprobación básica del formato.
  • password : entrada cuyo texto normalmente se oculta visualmente.
  • number : valor numérico con posibles límites min , max y step .
  • checkbox y radio : selecciones múltiples o mutuamente excluyentes, según la configuración.
  • required , minlength , maxlength , pattern : atributos de validación nativa.
  • name : nombre con el que se identifica el campo al enviar el formulario.
Diferencia entre GET y POST en formularios

GET se utiliza habitualmente para consultas que no deberían modificar el estado del servidor. Los parámetros suelen aparecer en la URL y pueden guardarse como marcadores o compartirse.

POST se utiliza para enviar datos al servidor para su procesamiento. No es cifrado por sí mismo: HTTPS protege la comunicación en tránsito. Tampoco debe asumirse que POST garantiza la privacidad o evita duplicados automáticamente.

Un formulario HTML estático no procesa datos por sí solo. Para almacenar información, autenticar usuarios o hacer operaciones sensibles se necesita un backend o un servicio apropiado.

04. Fundamentos de CSS

CSS (Cascading Style Sheets) describe la presentación de los elementos HTML. Se organiza mediante reglas compuestas por un selector y un bloque de declaraciones.

Sintaxis, selectores y combinadores 
/* Selector de tipo */
p { color: #334155; }

/* Selector de clase */
.card { padding: 1rem; }

/* Selector de identificador */
#main-content { max-width: 70rem; }

/* Descendiente */
.card p { line-height: 1.7; }

/* Hijo directo */
.menu > li { list-style: none; }

/* Estado interactivo */
a:hover { text-decoration: underline; }

/* Múltiples selectores */
h1, h2, h3 { line-height: 1.2; }

Los selectores de clase son una opción reutilizable habitual. Reserva los selectores por identificador para casos en los que realmente necesitas ese grado de especificidad o para relaciones con JavaScript.

Cascada, herencia y especificidad

Cuando varias reglas coinciden con un elemento, CSS resuelve el resultado según la cascada: origen e importancia de la regla, capas de cascada cuando existen, especificidad y orden de aparición, entre otros criterios aplicables.

La especificidad compara el peso de los selectores. En términos generales, un selector con identificador tiene más especificidad que uno con clase, y uno con clase más que uno de tipo. La herencia permite que algunas propiedades, como color y font-family , pasen de un elemento antecesor a sus descendientes. 

/* Menos específico */
p { color: #475569; }

/* Más específico */
.article p { color: #0f172a; }

/* Evita depender de !important para resolver cada conflicto */

Regla práctica: evita cadenas de selectores innecesariamente largas y el uso rutinario de !important . Una estructura consistente hace más fácil mantener el CSS.

Box model: content, padding, border y margin

El modelo de caja determina cuánto espacio ocupa un elemento. Con content-box , el ancho se aplica al contenido y el padding y el borde se suman al tamaño exterior. Con border-box , el ancho incluye contenido, padding y borde. 

*,
*::before,
*::after {
    box-sizing: border-box;
}

.card {
    width: 100%;
    max-width: 30rem;
    padding: 1.25rem;
    border: 1px solid #e2e8f0;
    margin-inline: auto;
}

El margen crea espacio externo; el padding crea espacio entre el contenido y el borde. El margen puede colapsar verticalmente en determinados contextos de bloque, por lo que no siempre se suman como se esperaría.

Unidades: px, rem, em, %, vw y vh
  • px : unidad CSS absoluta de referencia; útil para bordes finos y detalles pequeños.
  • rem : relativo al tamaño de fuente del elemento raíz; útil para tipografía y espaciado consistente.
  • em : relativo al tamaño de fuente del contexto que corresponda a la propiedad.
  • % : relativo al contexto definido por la propiedad y el elemento contenedor.
  • vw y vh : unidades relacionadas con el viewport; para alturas móviles, revisa también dvh cuando proceda.
  • fr : fracción del espacio disponible en CSS Grid. 
:root { font-size: 16px; }

.page-title { font-size: clamp(1.8rem, 4vw, 3rem); }
.container { width: min(100% - 2rem, 70rem); margin-inline: auto; }
.grid { display: grid; grid-template-columns: repeat(3, minmax(0, 1fr)); gap: 1rem; }
Variables personalizadas y organización del CSS

Las propiedades personalizadas permiten reutilizar valores y centralizar decisiones visuales, como colores, tamaños, sombras y radios de borde. 

:root {
    --color-primary: #0284c7;
    --color-text: #172033;
    --color-border: #e2e8f0;
    --radius-card: 0.75rem;
    --space-md: 1rem;
}

.card {
    padding: var(--space-md);
    border: 1px solid var(--color-border);
    border-radius: var(--radius-card);
    color: var(--color-text);
}

.button-primary {
    background: var(--color-primary);
}

Organiza los estilos por componentes o áreas, mantiene una convención de nombres y evita duplicar declaraciones que representan el mismo patrón visual.

05. Distribución: display, Flexbox y Grid

Las herramientas de layout permiten distribuir contenido según el eje principal, el eje transversal o una cuadrícula de filas y columnas. Elegir la técnica adecuada evita recurrir a márgenes artificiales y posicionamiento absoluto para organizar toda la interfaz.

Block, inline, inline-block y none
  • block : normalmente comienza en una nueva línea y ocupa el ancho disponible del contenedor.
  • inline : participa en el flujo de texto; ancho y alto no se comportan como en un bloque tradicional.
  • inline-block : fluye con el texto, pero admite dimensiones de caja.
  • none : elimina el elemento del flujo de layout y no lo muestra visualmente.
  • flex y grid : activan modelos de distribución flexibles y bidimensionales.

El atributo HTML hidden también representa que un elemento no está actualmente disponible para mostrarse. Esta guía utiliza una regla CSS explícita para garantizar que las vistas ocultas no se rendericen.

Flexbox: distribuir elementos en un eje

Flexbox resulta apropiado para alinear elementos en una fila o columna, distribuir espacio disponible y gestionar el crecimiento o la contracción de los elementos. 

.toolbar {
    display: flex;
    align-items: center;
    justify-content: space-between;
    gap: 1rem;
    flex-wrap: wrap;
}

.toolbar-actions {
    display: flex;
    align-items: center;
    gap: 0.5rem;
}

@media (max-width: 40rem) {
    .toolbar {
        align-items: stretch;
        flex-direction: column;
    }
}

Propiedades del contenedor: display , flex-direction , justify-content , align-items , flex-wrap y gap .

Propiedades de los elementos: flex , flex-grow , flex-shrink , flex-basis y align-self .

CSS Grid: filas, columnas y tarjetas

Grid está pensado para distribuir elementos en dos dimensiones. Es útil para galerías, paneles, dashboards y diseños con columnas que se adaptan al ancho disponible. 

.cards {
    display: grid;
    grid-template-columns: repeat(3, minmax(0, 1fr));
    gap: 1rem;
}

@media (max-width: 900px) {
    .cards {
        grid-template-columns: repeat(2, minmax(0, 1fr));
    }
}

@media (max-width: 600px) {
    .cards {
        grid-template-columns: minmax(0, 1fr);
    }
}

minmax(0, 1fr) ayuda a evitar que contenido largo fuerce la columna a ser más ancha de lo previsto. También son útiles grid-template-areas , auto-fit , auto-fill y minmax() .

Position, z-index y stacking context
  • static : posición normal por defecto.
  • relative : mantiene su espacio normal y permite desplazar el elemento; también puede actuar como referencia para descendientes absolutos.
  • absolute : se posiciona respecto de su bloque contenedor de posicionamiento y sale del flujo normal.
  • fixed : suele posicionarse respecto al viewport y permanece en esa ubicación al desplazarse.
  • sticky : combina el comportamiento normal con un umbral de fijación dentro de su contenedor de desplazamiento.

z-index no es una solución universal: los contextos de apilamiento pueden hacer que un valor elevado no supere a un elemento de otro contexto. Revisa también propiedades como transform , opacity y el contexto de posicionamiento.

06. Responsive design y estilos modernos

Un diseño adaptable reorganiza el contenido según el espacio disponible, sin asumir un único tamaño de pantalla. Los puntos de ruptura deben responder al diseño y al contenido, no únicamente a modelos concretos de dispositivos.

Media queries y enfoque mobile-first 
/* Estilos base: pantallas pequeñas */
.layout {
    display: grid;
    grid-template-columns: minmax(0, 1fr);
    gap: 1rem;
}

/* Añade columnas cuando el contenido tiene espacio */
@media (min-width: 48rem) {
    .layout {
        grid-template-columns: 16rem minmax(0, 1fr);
    }
}

/* Preferencias de accesibilidad */
@media (prefers-reduced-motion: reduce) {
    *, *::before, *::after {
        scroll-behavior: auto !important;
        animation-duration: 0.01ms !important;
        transition-duration: 0.01ms !important;
    }
}

Mobile-first significa diseñar primero los estilos base para pantallas estrechas y ampliar el layout mediante media queries cuando sea necesario. No implica que todos los sitios deban tener exactamente los mismos puntos de ruptura.

Imágenes, tipografía y contenido adaptable 
img, video {
    display: block;
    max-width: 100%;
    height: auto;
}

.page-title {
    font-size: clamp(1.8rem, 4vw, 3rem);
    line-height: 1.1;
}

.article {
    width: min(100% - 2rem, 72rem);
    margin-inline: auto;
}

.long-text {
    overflow-wrap: anywhere;
}

clamp() define un mínimo, un valor flexible y un máximo. Aun con un diseño fluido, verifica que las líneas no sean excesivamente largas, que los controles sigan siendo utilizables y que los textos amplíen sin recortes.

Estados interactivos y controles accesibles 
.button {
    border: 1px solid transparent;
    border-radius: 0.5rem;
    padding: 0.65rem 1rem;
    cursor: pointer;
}

.button:hover {
    filter: brightness(0.96);
}

.button:focus-visible {
    outline: 3px solid #38bdf8;
    outline-offset: 3px;
}

.button:disabled {
    cursor: not-allowed;
    opacity: 0.55;
}

No elimines el indicador de foco sin ofrecer una alternativa visible. Comprueba también contraste, tamaños de objetivo táctil, contenido en estados hover/focus y comportamiento con teclado.

08. Errores frecuentes y cómo diagnosticarlos

El CSS no se aplica

Revisa: la ruta del archivo en <link rel="stylesheet" href="..."> , el nombre exacto del archivo, la pestaña Network del navegador y los errores de carga. Comprueba también que el selector coincide con el HTML y que otra regla no lo sobrescribe.

El diseño se desborda horizontalmente

Causas comunes: anchos rígidos, elementos flex que no pueden encogerse, cadenas largas, imágenes grandes o columnas de Grid sin un mínimo flexible.

Soluciones a evaluar: max-width: 100% , min-width: 0 , minmax(0, 1fr) y overflow-wrap: anywhere . Evita esconder todo el desbordamiento con overflow-x: hidden sin localizar primero su causa.

Un elemento con z-index sigue quedando detrás

Inspecciona los contextos de apilamiento y los ancestros del elemento. Un valor de z-index muy alto no puede necesariamente superar otro contexto que lo contiene. Comprueba además el posicionamiento y propiedades como transform y opacity .

El formulario parece válido pero recibe datos incorrectos

La validación del navegador no es una frontera de seguridad. Valida los datos en el servidor, aplica las reglas de negocio, gestiona los errores y verifica permisos antes de operar con la información recibida.

Funciona localmente pero falla en GitHub Pages

Verifica las rutas relativas, el nombre exacto de cada archivo, las mayúsculas y minúsculas, que los recursos se hayan subido al repositorio y que la página esté configurada para desplegar desde la rama o carpeta correcta. Revisa la consola y Network para localizar errores 404.

09. Preguntas de entrevista: HTML y CSS

Intenta responder antes de desplegar cada elemento. Las respuestas son una base para explicaciones técnicas; añade ejemplos propios durante la preparación.

¿Cuál es la diferencia entre HTML, CSS y JavaScript?

HTML estructura y describe el contenido; CSS define su presentación y layout; JavaScript añade comportamiento, lógica e interacción. En una aplicación real, las tres tecnologías suelen colaborar, pero cumplen responsabilidades diferentes.

¿Qué diferencia hay entre elementos block e inline?

Un elemento con comportamiento block suele comenzar una nueva línea y ocupa el ancho disponible; uno inline participa en el flujo de texto y no acepta ancho y alto de la misma forma. CSS puede cambiar el comportamiento con la propiedad display .

¿Qué es HTML semántico y por qué importa?

Es utilizar elementos que expresan el significado de su contenido, como nav , main , article y footer . Mejora la estructura del documento, la accesibilidad y la mantenibilidad, y puede ayudar a los sistemas que interpretan la página.

¿Cuál es la diferencia entre class e id?

class agrupa elementos para reutilizar estilos o comportamientos. id identifica un elemento específico y debe ser único en el documento. Los selectores de id también tienen una especificidad mayor que los selectores de clase.

¿Qué es la cascada en CSS?

Es el conjunto de reglas que determina qué declaración prevalece cuando varias pueden aplicarse al mismo elemento. Intervienen factores como importancia, origen, capas de cascada, especificidad y orden. La herencia es un mecanismo relacionado, pero no es sinónimo de cascada.

¿Qué diferencia hay entre Flexbox y Grid?

Flexbox se orienta principalmente a la distribución a lo largo de un eje, mientras que Grid permite definir filas y columnas en dos dimensiones. Pueden combinarse: por ejemplo, Grid para una composición de tarjetas y Flexbox para alinear los controles dentro de cada tarjeta.

¿Qué es el box model y qué resuelve box-sizing: border-box?

El box model incluye contenido, padding, borde y margen. Con border-box , el ancho y alto declarados incluyen el contenido, padding y borde, lo que suele hacer más predecible el cálculo de dimensiones.

¿Qué significa responsive design?

Es diseñar interfaces que se adapten a diferentes tamaños de viewport y condiciones de uso. Combina layouts flexibles, imágenes adaptables, unidades relativas, media queries y pruebas reales en distintos tamaños.

¿Para qué sirve el atributo alt en una imagen?

Proporciona una alternativa textual a la imagen cuando no se puede ver o cuando una persona utiliza tecnologías de asistencia. El contenido debe comunicar el propósito de la imagen; si es solo decorativa, puede usarse alt="" .

¿Por qué no se debe confiar solo en la validación de formularios HTML?

Porque el usuario puede modificar la petición o evitar la validación del navegador. El backend debe comprobar formato, límites, reglas del negocio y autorización antes de procesar los datos.

¿Cómo mejorarías la accesibilidad de una página?

Utilizaría HTML semántico, etiquetas asociadas a campos, texto alternativo apropiado, contraste suficiente, navegación por teclado, foco visible, nombres accesibles y mensajes de error claros. Después probaría la página con teclado y herramientas de auditoría de accesibilidad, sin asumir que una puntuación automática garantiza conformidad completa.

¿Cómo diagnosticarías un estilo que no se aplica?

Inspeccionaría el elemento en las DevTools, comprobaría si el archivo CSS se cargó, verificaría el selector y observaría qué reglas aparecen anuladas. También revisaría errores de sintaxis, orden de carga y reglas más específicas.

Frontend y React

El frontend presenta datos y permite interacción accesible. En React, interfaces se construyen con componentes y estado; diseña límites de componentes claros y evita duplicar estado derivable.

Conceptos, herramientas y ejemplos

Componentes y props

Estado y renderizado

Si el orden cambia, el estado local puede asociarse al elemento equivocado. Prefiere una identidad estable de los datos.

¿Cuándo usar useEffect?

Para sincronizar con sistemas externos como subscriptions, timers o API cuando corresponde, no para calcular cada valor derivable.

¿Qué diferencia hay entre controlled y uncontrolled input?

Backend

Capas y dominio

API DESIGN

APIs y arquitectura web

Una API define un contrato entre sistemas. Diseña recursos, métodos, errores, paginación, autorización y versionado; documenta ejemplos para que clientes puedan integrarse de forma predecible.

Conceptos, herramientas y ejemplos

HTTP y códigos de estado

200 indica éxito general, 201 creación, 204 éxito sin cuerpo; 400 solicitud inválida, 401 no autenticada, 403 no autorizada, 404 no encontrado, 409 conflicto y 5xx fallo del servidor. El contrato concreto manda.

REST y recursos

Modela recursos con URLs coherentes y métodos HTTP apropiados. GET debe ser seguro y normalmente idempotente; PUT suele reemplazar estado de recurso e idempotente; PATCH modifica parcialmente; POST procesa o crea según contrato.

Autorización, CORS y rate limits

La autorización se valida en backend por recurso/acción. CORS controla acceso desde navegadores, no es autorización. Rate limiting protege capacidad y debe comunicarse de forma documentada.

Paginación, filtrado y versionado

Define orden estable, límites máximos y paginación cursor/offset según consulta. Cambios incompatibles requieren estrategia de versionado o evolución compatible.

OpenAPI y contratos

OpenAPI describe operaciones, schemas, seguridad y respuestas; genera documentación/clients y permite contract testing. Mantén la especificación sincronizada con la implementación.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

curl -i -H "Accept: application/json" https://api.example.com/v1/items
curl -i -X POST https://api.example.com/v1/items \
  -H "Content-Type: application/json" \
  -d '{"name":"demo"}'

Preguntas frecuentes y de entrevista

¿REST es lo mismo que HTTP?

No. HTTP es un protocolo; REST es un estilo arquitectónico. Una API web REST suele utilizar HTTP, pero no son sinónimos.

¿Qué es idempotencia?

Repetir una operación con la misma entrada produce el mismo efecto final previsto; es clave en reintentos de red.

¿Qué diferencia hay entre GraphQL y REST?

REST suele exponer recursos/endpoints; GraphQL permite solicitar campos mediante un schema/query language. Ambos necesitan autorización, límites y monitoreo.

¿Qué diferencia hay entre 401 y 403?

401 corresponde a autenticación ausente/inválida; 403 a rechazo por permisos. Algunas APIs pueden documentar variaciones.

¿Qué es CORS?

Política del navegador basada en encabezados que controla si un origen puede leer respuestas de otro origen; no reemplaza auth/autorización.

Fundamentos de datos

El trabajo con datos abarca captura, almacenamiento, limpieza, transformación, modelado, análisis y comunicación de resultados. La calidad y el significado del dato importan tanto como la herramienta.

Conceptos, herramientas y ejemplos

OLTP vs OLAP

Data lake, warehouse y lakehouse

Un data lake guarda datos en formatos variados; un warehouse ofrece estructuras optimizadas para analítica; lakehouse combina almacenamiento flexible con capacidades de gestión/consulta analítica. Son patrones, no garantías automáticas de calidad.

Calidad y linaje

Controla completitud, validez, consistencia, unicidad y frescura. Documenta origen, transformaciones y consumidores para saber qué dashboard o modelo se ve afectado al cambiar una fuente.

Batch vs streaming

Batch procesa conjuntos por lotes; streaming procesa eventos continuamente con latencia menor pero exige tratar orden, duplicados, late events, backpressure y re-procesamiento.

¿ETL o ELT?

Modelo dimensional con tabla de hechos y dimensiones, útil para consultas analíticas comprensibles y eficientes.

¿Qué es data lineage?

Registro de origen y transformaciones para rastrear cómo se produce y consume un dato.

¿Qué diferencia hay entre batch y streaming?

Batch prioriza procesamiento por lotes; streaming procesa eventos continuos y requiere gestionar retrasos y duplicados.

DATABASE QUERYING

SQL

SQL consulta y transforma datos relacionales. Para entrevistas, domina JOIN, agregaciones, NULL, CTE, funciones de ventana, índices y transacciones.

Conceptos, herramientas y ejemplos

JOIN y agregaciones

INNER JOIN devuelve coincidencias; LEFT JOIN conserva filas izquierdas sin correspondencia. Filtrar en WHERE vs ON puede cambiar los resultados de un outer join. GROUP BY agrega filas y HAVING filtra grupos.

NULL y lógica de tres valores

Usa IS NULL/IS NOT NULL, no = NULL . COUNT(*) cuenta filas; COUNT(columna) excluye valores NULL. COALESCE sustituye nulos siguiendo el tipo y semántica del motor.

CTE y funciones de ventana

WITH mejora legibilidad y puede representar pasos intermedios. Window functions calculan ranking, acumulados o comparaciones por partición sin colapsar filas como GROUP BY.

Índices y planes

Los índices aceleran ciertos accesos pero cuestan almacenamiento y escritura. Revisa EXPLAIN/plan, selectividad, filtros, joins, estadísticas y volumen real antes de optimizar.

Transacciones y ACID

Atomicidad, consistencia, aislamiento y durabilidad describen propiedades de transacciones. Bloqueos y niveles de aislamiento afectan concurrencia y anomalías posibles.

Ejemplo práctico

Ejemplo de referencia: ajusta los nombres, valores y permisos a tu entorno de laboratorio antes de ejecutarlo. 

SELECT department_id, COUNT(*) AS employee_count, AVG(salary) AS avg_salary
FROM employees
WHERE active = TRUE
GROUP BY department_id
HAVING COUNT(*) >= 5
ORDER BY avg_salary DESC;

Errores frecuentes y diagnóstico

JOIN duplica filas

Comprueba cardinalidad y claves; puede existir relación uno-a-muchos o duplicados en la dimensión. No elimines duplicados sin verificar semántica.

Resultado excluye filas NULL

Una comparación estándar con NULL no devuelve TRUE. Utiliza IS NULL y revisa filtros en WHERE que puedan convertir un LEFT JOIN en comportamiento de INNER JOIN.

Preguntas frecuentes y de entrevista

WHERE vs HAVING?

WHERE filtra filas antes de agrupar; HAVING filtra grupos después de agregación.

INNER JOIN vs LEFT JOIN?

INNER conserva solo coincidencias; LEFT conserva todas las filas izquierdas y completa con NULL donde no haya coincidencia derecha.

COUNT(*) vs COUNT(column)?

COUNT(*) cuenta filas; COUNT(column) cuenta valores no NULL de esa columna.

¿Cómo buscar duplicados?

Agrupa por la clave candidata y usa HAVING COUNT(*) > 1; define la clave de negocio antes de eliminar registros.

¿Qué es una función de ventana?

Calcula valores sobre una ventana de filas relacionadas sin colapsar el nivel de detalle principal.

¿Por qué una consulta no usa índice?

Puede haber baja selectividad, estadísticas obsoletas, expresión sobre la columna, conversión implícita, costos estimados o una estrategia más eficiente sin ese índice.

DATABASE SYSTEMS

Bases de datos

El diseño de datos implica modelo, integridad, transacciones, rendimiento, backups, replicación y control de acceso. Elige el motor según patrones reales y requisitos de consistencia.

Conceptos, herramientas y ejemplos

Relacionales

PostgreSQL, MySQL y SQL Server modelan datos mediante tablas, restricciones y relaciones. Aprende claves primarias/foráneas, normalización, índices, joins, aislamiento y recuperación.

NoSQL

Documentos, clave-valor, columnas anchas y grafos resuelven patrones diferentes. NoSQL no significa “sin esquema” ni elimina la necesidad de modelado, índices y estrategia de backup.

Redis y caché

Redis ofrece estructuras en memoria y se usa en caché, coordinación o colas según configuración. Define TTL, invalidación, límites de memoria, persistencia y comportamiento ante caída.

Backups, réplica y HA

Replicación ayuda a disponibilidad/lectura, pero no reemplaza backups contra borrado o corrupción. Prueba restauraciones y define RTO/RPO con el negocio.

Índices y transacciones

Un índice acelera consultas seleccionadas y penaliza escrituras/almacenamiento. Entiende ACID, locks, deadlocks, isolation y conexiones/pooling.

Preguntas frecuentes y de entrevista

¿Normalización o desnormalización?

Normalizar reduce redundancia y anomalías; desnormalizar puede acelerar lecturas a costa de consistencia y mantenimiento. Decide según consultas y carga.

¿Replica equivale a backup?

No. Una réplica puede copiar borrados o corrupción; los backups permiten restaurar un punto anterior.

¿Qué es un índice compuesto?

Índice sobre varias columnas; el orden afecta qué filtros/ordenamientos pueden aprovecharlo según motor y consulta.

¿Qué es un deadlock?

ETL, ELT y modelado de datos

Un pipeline debe conservar trazabilidad, validar calidad y manejar cambios de schema y re-procesamientos. Modelar comienza por definir el grano, las entidades y las consultas esperadas.

Conceptos, herramientas y ejemplos

ETL vs ELT

ETL transforma antes de cargar; ELT carga datos y transforma dentro de la plataforma de destino. ELT usa capacidad del warehouse; ETL puede ser preferible por requisitos de privacidad, formato o preprocesamiento.

Modelo dimensional

La tabla de hechos registra eventos con grano definido; dimensiones describen entidades. Incluye claves, fechas, medidas aditivas/no aditivas y política para dimensiones lentamente cambiantes.

Data quality

Valida nulls inesperados, rangos, unicidad, relaciones, frescura y volumen. Un test debe expresar regla de negocio y explicar cómo tratar fallos.

Incrementalidad y backfill

Procesamiento incremental reduce costo pero necesita watermark/clave estable y reconciliación. Backfill repuebla periodos históricos sin duplicar o borrar resultados inadvertidamente.

¿Cómo hacer un backfill seguro?

Determina rango/particiones afectadas, haz ejecución de prueba, utiliza lógica idempotente, compara conteos/métricas y coordina dependencias downstream.

Fundamentos de ciberseguridad

La seguridad protege confidencialidad, integridad y disponibilidad. Diseña controles por capas y prioriza riesgos reales, en lugar de depender de una única barrera.

Conceptos, herramientas y ejemplos

CIA triad y defensa en profundidad

Confidencialidad limita quién accede; integridad protege contra cambios no autorizados; disponibilidad mantiene el servicio. Defensa en profundidad combina identidades, red, endpoint, datos, monitoreo y respuesta.

Vulnerabilidades y parches

Inventaría activos y dependencias, prioriza por exposición, explotación e impacto, aplica parches en entornos de prueba y verifica luego. CVSS ayuda a describir severidad, pero no sustituye el análisis de contexto.

Modelado de amenazas

Identifica activos, límites de confianza, actores, vectores y controles. STRIDE es una técnica para explorar spoofing, tampering, repudiation, information disclosure, denial of service y elevation of privilege.

Respuesta ante incidentes

Detecta y valida, contiene, erradica, recupera y aprende. Preserva logs/evidencia, registra línea temporal y coordina comunicaciones; no elimines evidencia antes de investigar.

Secure SDLC

Incluye revisión de código, análisis de dependencias, secrets scanning, SAST/DAST cuando corresponda, threat modeling y políticas de release. Automatiza controles proporcionados al riesgo.

Preguntas frecuentes y de entrevista

¿Qué es defensa en profundidad?

Aplicar capas independientes para que un fallo no exponga todo el sistema.

¿Qué diferencia hay entre amenaza, vulnerabilidad y riesgo?

Amenaza es un agente/evento potencial; vulnerabilidad es una debilidad; riesgo combina probabilidad e impacto en un contexto.

¿Qué harías si aparece un secreto en Git?

Revocarlo/rotarlo primero, determinar alcance y uso, revisar logs y accesos, eliminarlo del historial si corresponde y evitar que se vuelva a introducir.

¿Para qué sirve un pentest?

Evalúa de forma autorizada si controles y aplicaciones pueden vulnerarse; sus hallazgos deben validarse, priorizarse y remediarse.

IAM, roles y permisos

IAM define qué principal puede ejecutar qué acción sobre qué recurso bajo qué condiciones. Evalúa identidad efectiva, ámbito y políticas heredadas al diagnosticar permisos.

Conceptos, herramientas y ejemplos

Identidad, autenticación y autorización

Principal puede ser usuario, grupo, role, service account o workload. Autenticación confirma identidad; autorización evalúa permiso para una acción sobre un recurso.

Principio de mínimo privilegio

Concede solo acciones necesarias al alcance más pequeño posible. Sustituye permisos amplios por policies específicas apoyadas en logs, casos de uso y pruebas.

Federación, roles y credenciales temporales

Evaluación de políticas

Preguntas frecuentes y de entrevista

¿Role vs user?

Conceder solamente los permisos necesarios y retirarlos cuando dejan de ser necesarios.

¿Por qué hay AccessDenied aunque exista Allow?

Puede existir deny explícito, SCP/guardrail, permissions boundary, session policy, condición fallida, recurso incorrecto o política fuera del ámbito esperado.

¿Cómo se evita guardar claves de cloud en CI?

Usando federación/OIDC y roles temporales con confianza restringida al repositorio, branch, environment y workflow esperados.

IDENTITY PROTOCOLS

OAuth 2.0, OIDC, SAML y JWT

Los protocolos de identidad resuelven problemas distintos. OAuth 2.0 delega autorización; OpenID Connect añade una capa de identidad; SAML se usa mucho en federación empresarial; JWT es un formato de token, no un protocolo de autenticación por sí solo.

Conceptos, herramientas y ejemplos

OAuth 2.0

Permite que un cliente obtenga acceso limitado a un recurso mediante access tokens. Para aplicaciones modernas usa flujos adecuados al tipo de cliente, como Authorization Code con PKCE para clientes públicos; evita patrones obsoletos o flujos inseguros.

OpenID Connect (OIDC)

OIDC añade autenticación e ID Token sobre OAuth 2.0. Valida firma, issuer, audience, expiry, nonce cuando aplica y usa discovery/JWKS de un issuer confiable.

SAML 2.0

Protocolo basado en assertions XML para intercambio de identidad, común en SSO empresarial. Valida firma, issuer, audiencia, destinatario, tiempo y configuración de trust.

JWT

JSON Web Token contiene claims y una firma o protección criptográfica. Codificar no es cifrar; no almacenes información secreta en un JWT firmado sin cifrar.

Sesiones y cookies

Usa HTTPS, HttpOnly, Secure y SameSite según contexto; protege sesión frente a fixation/CSRF y define expiración y revocación apropiadas.

Preguntas frecuentes y de entrevista

OAuth vs OIDC?

OAuth delega autorización para acceder a recursos; OIDC añade funciones de autenticación e ID Token.

¿Un JWT está cifrado?

No necesariamente: los JWT firmados suelen ser legibles; la firma protege integridad/autenticidad, no confidencialidad.

¿Qué validar en un ID Token?

Firma usando claves confiables, issuer, audience, exp, nonce y claims relevantes; no aceptes cualquier token sólo porque tenga forma JWT.

¿Qué es PKCE?

Mecanismo que liga el código de autorización al cliente que inició el flujo y mitiga interceptación del código en clientes públicos.

¿Qué diferencia hay entre ID Token y Access Token?

ID Token comunica autenticación/claims al cliente OIDC; Access Token presenta autorización/acceso ante un recurso protegido. No los intercambies indiscriminadamente.

Secretos y cifrado

Conceptos, herramientas y ejemplos

Secret manager

Las señales operacionales permiten saber si un sistema funciona y explicar por qué no. Correlaciona métricas, logs, trazas, cambios y contexto de despliegue.

Conceptos, herramientas y ejemplos

Métricas

SOFTWARE QUALITY

Testing y QA

Las pruebas reducen riesgo cuando detectan fallos relevantes con una señal rápida y estable. Diseña una pirámide equilibrada y evita depender solo de pruebas end-to-end lentas.

Conceptos, herramientas y ejemplos

Unitarias e integración

Unit tests validan lógica aislada; integración comprueba interacción entre módulos, bases o APIs. Usa dobles de prueba cuando aporten aislamiento sin simular todo el sistema innecesariamente.

E2E y contract tests

E2E valida flujos del usuario a través del sistema y suele tener mayor costo; contract tests verifican compatibilidad entre servicios sin requerir siempre un sistema completo.

Flaky tests

Una prueba flaky falla de forma no determinista. Busca dependencia del tiempo, orden, recursos compartidos, concurrencia y datos externos; no normalices reintentos que ocultan el fallo.

Calidad en CI

Ejecuta checks rápidos antes, divide suites lentas, guarda reportes y falla ante criterios claros. Una cobertura alta no demuestra que las aserciones prueben comportamientos valiosos.

Preguntas frecuentes y de entrevista

¿Mocks vs integración real?

Mocks son rápidos y controlables, pero pueden divergir del sistema real. Complementa con pruebas de integración en límites críticos.

¿Qué es regression testing?

Pruebas que verifican que un cambio no haya roto comportamientos previamente correctos.

¿Qué significa code coverage?

Proporción de líneas, ramas u otros elementos instrumentados ejecutados por pruebas; es una señal, no una medida directa de calidad.

¿Cómo gestionar una prueba flaky?

Identifica fuente de no determinismo, estabiliza datos/clock/concurrencia y registra la tasa de fallo; no ocultes indefinidamente el problema con retries.

SOFTWARE ARCHITECTURE

Arquitectura de software

La arquitectura define límites, dependencias, persistencia, comunicación, resiliencia y trade-offs para cumplir requisitos de calidad del sistema.

Conceptos, herramientas y ejemplos

Requisitos funcionales y no funcionales

Funcionales describen qué hace el sistema; no funcionales incluyen disponibilidad, latencia, capacidad, seguridad, mantenibilidad y costo. Convierte objetivos vagos en métricas y escenarios verificables.

Acoplamiento y cohesión

Busca componentes con responsabilidad clara y contratos estables. Bajo acoplamiento facilita cambiar una parte sin propagar cambios; alta cohesión mantiene funciones relacionadas juntas.

Monolito modular y microservicios

Un monolito modular puede simplificar transacciones, despliegues y depuración. Microservicios permiten autonomía por dominio, pero incorporan red, observabilidad distribuida, consistencia eventual y operación adicional.

Resiliencia distribuida

Usa timeouts, límites de concurrencia, retries con backoff y jitter cuando sean seguros, circuit breakers y bulkheads. Evita retries ilimitados que agraven saturación.

Arquitectura evolutiva

Registra decisiones con contexto y alternativas (ADR). Revisa los supuestos cuando cambien escala, equipo, riesgo o requisitos; evita optimizar prematuramente un sistema sin mediciones.

Preguntas frecuentes y de entrevista

¿Cómo elegir monolito o microservicios?

Según límites de dominio, necesidad de despliegue independiente, capacidad del equipo, escala y costo de operar sistemas distribuidos.

¿Qué es eventual consistency?

Los nodos/lecturas pueden observar estados distintos durante un periodo antes de converger. La aplicación debe tratar ese comportamiento explícitamente.

¿Qué es un ADR?

Architecture Decision Record: documento breve con contexto, decisión, alternativas y consecuencias de una decisión arquitectónica.

¿Qué es un single point of failure?

Componente o dependencia cuya falla causa la interrupción del sistema o función crítica.

ARCHITECTURE PATTERNS

Patrones de arquitectura

Los patrones son herramientas para resolver problemas recurrentes, no recetas universales. Documenta el problema que resuelven y los costos que introducen.

Conceptos, herramientas y ejemplos

Layered / clean architecture

Separa presentación, dominio y adaptadores. La regla de dependencias limita que el núcleo del negocio dependa directamente de infraestructura concreta.

Event-driven architecture

Productores publican eventos y consumidores reaccionan. Diseña idempotencia, schemas, orden, retries, DLQ, observabilidad y ownership del evento.

CQRS y event sourcing

CQRS separa modelos de lectura y escritura; event sourcing conserva eventos como fuente de estado. Ambos introducen complejidad de consistencia, versionado y reconstrucción, por lo que requieren una necesidad clara.

Caching

Cache-aside carga bajo demanda; write-through actualiza el caché en la ruta de escritura; CDN cachea contenido cerca del usuario. Define TTL, invalidación, tolerancia a stale data y protección de datos privados.

Saga y circuit breaker

Saga coordina transacciones distribuidas mediante pasos/compensaciones; circuit breaker evita repetir llamadas a dependencias que fallan. Ambos necesitan observabilidad y manejo explícito de estados intermedios.

Preguntas frecuentes y de entrevista

¿Qué problema resuelve un message queue?

Desacopla productor/consumidor, suaviza picos y habilita trabajo asíncrono; añade latencia, reintentos y necesidad de idempotencia.

¿Qué diferencia hay entre sync y async?

Síncrono espera resultado en la misma interacción; asíncrono separa ejecución/resultado y puede procesarse más tarde.

¿Cache invalida datos automáticamente?

No necesariamente. TTL, invalidación y sincronización deben diseñarse; caching mejora rendimiento a costa de complejidad y posible obsolescencia.

¿Cuándo evitar microservicios?

Cuando el dominio aún cambia rápidamente, el equipo es pequeño o el costo distribuido supera la autonomía que se necesita.

OPERATIONS & SUPPORT

Troubleshooting: método de diagnóstico

Un buen diagnóstico limita el alcance del fallo, recopila evidencia, formula una hipótesis y cambia una variable a la vez. Prioriza restaurar el servicio de forma segura y documentar el aprendizaje.

Conceptos, herramientas y ejemplos

1. Delimitar impacto

¿Quién falla, desde dónde, desde cuándo, a qué endpoint y en qué proporción? Distingue fallo global de un usuario, región, dispositivo, versión o dependencia particular.

2. Validar el recorrido

Comprueba DNS, rutas, conexión TCP/TLS, balanceador, backend, dependencias y datos. En sistemas distribuidos, usa request ID y timestamps para correlacionar eventos.

3. Comparar cambios recientes

Despliegues, configuración, DNS, credenciales, certificados, reglas de red, cuotas y cambios de schema son candidatos. Correlación temporal no prueba causalidad: valida la hipótesis.

4. Mitigar y recuperar

Considera rollback, failover o reducción de tráfico con plan definido. Evalúa efectos sobre datos y consistencia antes de revertir; comunica el estado a interesados.

5. Prevenir repetición

Documenta causa contribuyente, detección y tiempo de recuperación. Crea una alerta, test, control o runbook con responsable y fecha, no solo una nota genérica.

Preguntas frecuentes y de entrevista

¿Qué haces primero en un incidente?

Determinar alcance e impacto, proteger datos/usuarios y asignar responsabilidades; recoge evidencia antes de ejecutar cambios disruptivos.

¿Cómo evitas cambiar demasiadas cosas?

Formula hipótesis, prueba una variable controlada y compara resultado contra una línea base.

¿Cuándo usar rollback?

Cuando una versión/configuración reciente es la causa probable y revertir resulta seguro; evalúa migraciones de datos y compatibilidad.

¿Qué debe contener un ticket técnico?

Síntoma, impacto, cuándo ocurre, pasos para reproducir, entorno/versión, evidencias, cambios recientes, pruebas realizadas y siguiente acción.

Busca siglas y definiciones de uso frecuente. Al estudiar un término, vincúlalo con un escenario, una herramienta y un posible error operativo.

Conceptos, herramientas y ejemplos

Contrato por el que componentes de software intercambian solicitudes y respuestas o invocan operaciones.

CI/CD · Continuous Integration / Delivery / Deployment

Prácticas para validar cambios e integrar, preparar o automatizar la entrega de software.

DNS · Domain Name System

Sistema distribuido para consultar registros asociados a nombres, como direcciones IP.

IaC · Infrastructure as Code

Definición versionable de infraestructura que puede revisarse, validarse y aplicarse automáticamente.

IAM · Identity and Access Management

Controles para autenticar principales y autorizar sus acciones sobre recursos.

RTO / RPO

RTO: tiempo objetivo para recuperar un servicio. RPO: pérdida de datos tolerable expresada como un intervalo de tiempo.

SLI / SLO / SLA

SLI es la medida; SLO es un objetivo para esa medida; SLA es un compromiso contractual o formal con condiciones.

WAF · Web Application Firewall

Firewall para tráfico web capaz de evaluar solicitudes HTTP y aplicar reglas frente a patrones de ataque; no reemplaza corregir fallas de aplicación.

JWT · JSON Web Token

Formato compacto para representar claims; una firma no equivale a cifrado y el contenido puede ser legible.

MTTR / MTBF

MTTR suele medir tiempo medio de reparación/recuperación; MTBF, tiempo medio entre fallos. Define exactamente las métricas en el contexto usado.
